# TRYNKA — checklist ігрового процесу (staging)

Перевіряти тільки на окремому тестовому столі з тестовими фішками. **Не запускати
автоматичні ставки, RPC або навантажувальні запити проти реальних користувачів.**

## 1. Ставки та банк

- Два гравці вносять анте. Банк збільшується рівно на суму анте, без подвоєнь після оновлення сторінки.
- Підтримка: з балансу списується лише сума, дозволена сервером; банк збільшується на ту саму суму.
- Підвищення: ставка менша/рівна поточній або вища за серверний ліміт відхиляється без змін банку.
- Подвійне натискання чи повтор RPC з однаковим nonce: не створює другої оплати.
- Пас останнього суперника завершує раунд один раз; повторний показ результату не змінює баланс.

## 2. Темна, свара, вскриття

- Темна: сервер перевіряє, кому дозволені дії, і повертає авторизований стан.
- Свара між останніми учасниками: інші гравці можуть приєднатися у відведений час за серверним внеском; кожен внесок нараховується один раз.
- Вскриття: картки суперника показуються лише учасникам, яким сервер дозволив їх побачити.
- Після вскриття відкриті карти зникають перед новою роздачею і не потрапляють до іншого столу.

## 3. Перепідключення та таймери

- Розпочати партію удвох → вимкнути Wi-Fi/дані на 10–60 секунд → відновити.
- Гравець залишається **за тим самим столом**, карти і банк відповідають останньому серверному snapshot.
- Realtime status CHANNEL_ERROR/TIMED_OUT/CLOSED: повторна підписка без повторного join, без нових ставок.
- При поверненні вкладки після сну Android стан перезчитується.
- Під час відключення не дозволяти надсилати нову ставку з простроченого стану.
- Вихід зі столу під час запланованої повторної підписки: немає підключення назад.
- Стрибок таймера та завершення ходу: **рішення ухвалює сервер**, а не клієнтський інтервал.

## 4. Повторна роздача, бот, 100+ відвідувачів

- Почати новий раунд, не створюючи двох паралельних роздач та подвоєнь банку.
- Перевірити тайм-аут бота, два одночасні кліки, обрив мережі на переході раунду.
- Для 100+ користувачів проводити **окремий staging-тест** з лімітами RPS, метриками latency/p95, частки помилок, кількості активних Realtime-каналів та обмеженням витрат Supabase.

## Автоматична перевірка в PR

- `tests/room-recovery.test.mjs`: відмова/відновлення каналу, duplicate retry, offline, stale callback, leave, backoff.
- `tests/*.spec.js`: mobile 360/393 + desktop, карти/банк/кнопки/вскриття.
- Ці тести **не є** реальним інтеграційним тестом PostgreSQL/Supabase RPC. Для банку й свари потрібна ізольована staging БД і два тестові акаунти.
