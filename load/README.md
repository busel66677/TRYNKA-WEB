# TRYNKA: 100–150 користувачів (тільки staging)

**Не запускайте навантаження проти trinka.pp.ua або бойового Supabase.**
Цей набір не виконує ставки/роздачу/виплати. Він вимірює тільки серверні
читання `get_room_game_snapshot` з **окремої staging-бази**.

## Передумови

1. Підготувати окремий staging Supabase-проєкт із тестовими обліковими
   записами й синтетичними фішками. Створення staging-проєкту/гілки
   може коштувати грошей, тож **не створювати без погодження бюджету**.
2. Надати щонайменше N унікальних JWT тестових облікових записів.
   Дані JWT/ключі лише через змінні середовища або менеджер секретів:
   **не комітити**, **не надсилати в чат**.
3. Для кожного JWT надати ID тестового столу, де відповідний користувач
   уже учасник або спостерігач. В одному столі не більше 8 гравців.
   Для 100 гравців потрібно щонайменше 13 столів, для 150 — 19.
4. Встановити k6: https://grafana.com/docs/k6/latest/set-up/install-k6/

## Параметри k6

- `STAGING_SUPABASE_URL`: строго HTTPS URL іншого Supabase-проєкту.
- `STAGING_CONFIRM`: `STAGING_ONLY_I_ACCEPT_THE_TEST_LOAD`.
- `STAGING_PUBLISHABLE_KEY`: тільки публічний ключ staging.
- `STAGING_JWTS`: розділені комою JWT для окремих тестових користувачів.
- `STAGING_ROOM_IDS`: розділені комою ID тестових столів **у тому ж
  порядку**, що й JWT.
- `LOAD_VUS`: 10, 25, 50, 100 або 150; максимум 150.
- `LOAD_DURATION`: від `1m` до `5m`.

Запускати після встановлення секретів у **локальному** середовищі:

```sh
LOAD_VUS=10 LOAD_DURATION=1m k6 run load/read-only-snapshot.k6.js
```

Послідовно пройти 10 → 25 → 50 → 100 → 150 VU із паузами для
аналізу метрик, не підвищувати навантаження при помилках.

## Критерії та обмеження

- Для цієї перевірки: `p95 < 1500 ms`, частка HTTP-помилок менше 2%,
  успішність перевірок вище 98%; досліджувати timeout і 429/5xx.
- Контролювати DB CPU, активні запити, Realtime connections, план
  Supabase і вартість. Результати зберігати **без JWT чи відповідей API**.
- Окремо запустити e2e-тести двох учасників: анте, підвищення, темна,
  свара, вскриття, тайм-аут, пас, нова роздача, розрив і повернення мережі.
- Цей k6-сценарій **не доводить** готовності до 100 одночасних активних
  гравців і не тестує підписки Realtime; він перевіряє лише одночасне
  читання snapshot. Для повного висновку потрібна staging-навантажувальна
  перевірка Realtime та транзакцій із тестовими фішками.

## Поточний аудит індексів

Supabase Database Advisors попереджає про додаткові FK-індекси.
Деякі ключові запити вже мають індекси (наприклад, `game_rounds(room_id,id)`
та `room_players(user_id,room_id)`). Не додавати всі індекси бездумно:
спочатку зібрати query plans/metrics на staging і тільки після цього
запропонувати контрольовану міграцію.

https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys
